# ADR-008：信任继承（设备引荐）

- 状态：已采纳（2026-10-29，核心 `core/intro`）
- 背景：用户只有自己的设备。之前每对设备都要单独配对：设备 A 和 B 已配对，新设备 C 和 A 配对后，B 并不认识 C，还要再和 C 配一次。用户的要求是：只要 C 和 A 配对过，B 就默认信任 C，并自动完成配对；以后新加入的设备也一样。

## 决定

已配对的两台设备每次建立连接时，都把自己信任的其他设备告诉对方，对方直接把这些设备加为「已配对」。这样做的效果：

- 和网里**任意一台**设备配对一次就够了。其他设备在下一次和它连上时，就会学到新设备。
- 已经存在的设备网，升级之后也会自动连成全网。

**传什么**：一条普通的 `control` 事件 `{"action":"introduce","peers":[…]}`，走已经认证的 mTLS 链路。每个设备包含：设备 ID、名字、平台、证书指纹、tailnet 地址、端口。旧版核心会忽略这种事件（它的 `xfer` 只处理 `file_*` 动作）。

**接收时的规则**（`intro.Service.accept`）：

1. 只接受来自**已配对**对端的引荐。
2. 字段必须合法：设备 ID 格式、指纹格式（43 位 base64url）、平台是已知值、名字不超过 64 字符、地址在 tailnet 范围内。桌面设备还必须带地址和端口，否则无处拨号。
3. **本机移除过的设备**（指纹在吊销表里）不会被重新加入。要恢复，只能由用户重新配对。
4. 已经认识的设备（设备 ID 或指纹相同）保持原样，不会被覆盖。
5. 两台都只拨号、不监听的设备（Android 与 Android）不互相引荐，因为它们永远连不上。
6. 新记录的默认值和普通配对相同：处理策略「只通知」，密码库同步开启。
7. 核心设置 `trust_introductions`（`on` 或 `off`，默认 `on`）可以关闭「接受引荐」。

**加固**：服务端认证对端时，除了按指纹找到记录，还要求证书公钥推导出的设备 ID 与记录里的一致（`peer/server.go`）。这样，引荐方即使谎报了设备 ID，对方也会被拒绝。拨号这一侧本来就按指纹锁定对方的证书。

**界面**：新事件 `peer.introduced`，字段为 `device_id`、`name`、`platform`、`via_device_id`、`via_name`。三端收到后刷新设备列表，并弹出通知：「X 介绍了 Y，已把它加为已配对设备。不认识的话，请在设备页解除配对。」

## 代价和风险

- **信任变成传递的**：网里任何一台设备被攻破，攻击者都可以把自己的设备「引荐」给其他所有设备。之后它能：
  - 收到你的剪贴板；
  - 拿到加密的密码库文件，主密码仍然保护着它；
  - 收发文件，接收文件仍要逐个确认。

  这是用户为了方便明确要的取舍。关闭的办法是把 `trust_introductions` 设为 `off`；三端的设置界面暂时还没有这个开关。
- **移除只在本机生效**：在 A 上解除和 C 的配对，B 不会跟着解除。不过 C 不会被 B 重新引荐回 A，因为 A 已经吊销了 C 的指纹。要让 C 彻底离开整个网，需要在每台设备上分别移除它。不做「撤销传播」是有意的：一台被攻破的设备不应该能把你的其他设备互相踢掉。

## 验证

`core/intro/intro_test.go` 用真实引擎和环回 mTLS 测试了以下场景：

- A 认识手机 B 和 Mac C，B、C 自动互相信任，并直接连上；
- 本机吊销过的设备不会被带回来；
- 开关关闭时，什么也不加；
- 两台手机之间不互相引荐。

另外，`go test ./...` 全部通过。
