# 富文本编辑器与 Markdown：night-clip-notes

> 决策记录：[ADR-002](adr/002-rich-text-and-markdown.md)。同步对正文的要求见 [sync-model.md](sync-model.md) §2。

## 1. 核心问题

用户要求**同时**支持"富文本编辑器"和"Markdown"。由于两端（Windows WPF、Android Compose）技术栈不同，最容易出错的做法是：各端各选一个富文本控件，直接存 HTML 或富文本私有格式，再"顺便"导出 Markdown。这样会带来三个问题：

1. 两端渲染不一致（表格、嵌套列表、代码块、任务列表）。
2. 双向转换丢信息且无法审计（哪一次编辑丢了格式？）。
3. 同步时无法判断"只是渲染差异"还是"真实内容差异"（导致误冲突）。

## 2. 决定：Markdown 是唯一权威存储

- **存储**：每篇笔记的 `body` 就是**规范化 Markdown 文本**（UTF-8）。没有第二份"富文本真源"。
- **编辑**：两端都**编辑 Markdown**——要么是源码视图（语法高亮），要么是"所见即所得但底层是 Markdown 的块编辑器"。富文本控件只负责**渲染与输入映射**，不产生独立格式。
- **规范化**：写入前统一做规范化（`body_norm`），保证跨端字节一致：
  - 行尾统一 `\n`；
  - 标题 `# ` 后一个空格；列表符号统一 `-`；有序列表保持数字；
  - 强调符统一 `*`；代码围栏统一 ```` ``` ```` 且不省略语言标注；
  - 表格对齐行补齐；行尾空白剔除；连续空行折叠为一行；
  - 引用块 `> ` 嵌套规范。
- **哈希对象**：`rev_id` 与冲突判断都基于 `body_norm` 的 SHA-256，**不基于渲染后的 HTML**（渲染差异不制造冲突）。
- **兼容子集**：**CommonMark + GFM 子集**——标题、段落、强调/加粗/删除线、行内代码、代码块（带语言）、引用、有序/无序/任务列表、链接、图片、表格、分隔线。**不支持**的语法（如脚注、数学公式、HTML 内联块、自定义容器）的处理方式见 §5。

> **实现与本节的出入**（`core/notes/markdown`，细节见该包文档）：引用式链接不解析（定义原样保留为块，`[a][b]` 保持文本）、裸 URL 不自动链接；`__x__` 按 CommonMark 是加粗，会变成 `**x**`（所以 `__init__.py` 会变成 `**init**.py`，行内代码不受影响）；容器与行内嵌套各限 16 层，更深的当文本；多行 setext 标题合并成一行 ATX 标题；紧凑列表在无法保持紧凑时写成松散列表；相邻的两个列表交替使用 `-`/`*`、`1.`/`1)` 以免被合并；NUL 变 U+FFFD，U+FEFF 被删除。代码块不去除行尾空白（保留原样），硬换行 `␠␠⏎` 写成 `\`+换行。规范形式的任何改变都会让新旧版本互相拒收修订，见 [sync-model.md](sync-model.md) §8。

## 3. 块模型：编辑与合并的公共基础

为了实现"富文本编辑"和"块级合并"（[sync-model.md](sync-model.md) §4.1），核心把 Markdown 解析为**块列表**，每个块有稳定 id：

| 层 | 内容 | 谁产生 |
| --- | --- | --- |
| 块（block） | 段落、标题、列表、代码块、引用、表格、图片 | 核心的 Markdown 解析器 |
| 行内（inline） | 强调、链接、行内代码 | 核心 |
| 块 id | `sha256(块类型 + 规范化块内容)`，编辑后内容变化即新 id | 核心 |
| 渲染指令 | 壳需要的结构化数据（`notes.render` 返回），**不是 HTML** | 核心 |

- 壳通过 `notes.render(note_id)` 拿到块列表与渲染指令，富文本控件按块渲染、按块编辑；编辑完成后壳把**该块的 Markdown 文本**回传（`notes.update` 的 `patch`），核心重新规范化并计算新 `rev_id`。
- 这样做的收益：编辑态是富文本体验，数据层是纯 Markdown，合并是块级确定性操作，三件事不互相绑死。

## 4. 编辑器选型（候选，Phase 0 决定）

> 选型标准：许可证宽松、长期维护、能"底层持有 Markdown 而不是 HTML"、能按块编辑、Compose / WPF 有可用控件。**本阶段不引入任何依赖**，只列候选。

### 4.1 Windows（WPF）

| 方案 | 编辑方式 | 优点 | 风险 | 结论 |
| --- | --- | --- | --- | --- |
| 自带 `RichTextBox`(FlowDocument) + 自写 Markdown ↔ FlowDocument 映射 | 所见即所得 | 无新增依赖 | 双向映射要自己写且会丢格式；FlowDocument 不是 Markdown 模型 | 不推荐（与 §2 冲突） |
| WebView2 宿主 MonoMarkdown/CodeMirror 类编辑器 | 源码 + 预览 | 生态成熟、与 Android 一致性好 | 引入 WebView 运行时与 JS 链路；启动开销 | 备选 |
| 纯 WPF 块编辑器（每块一个编辑控件，自写渲染） | 所见即所得 | 完全可控、与核心块模型一一对应、无 WebView | 开发量大（表格/列表/代码块交互） | **推荐（渐进）**：先源码 + 预览两栏，再升级块编辑 |

### 4.2 Android（Kotlin Compose）

| 方案 | 编辑方式 | 优点 | 风险 | 结论 |
| --- | --- | --- | --- | --- |
| `BasicTextField` + `AnnotatedString` 自写语法高亮/块渲染 | 源码 + 预览 | 零依赖、可控 | 编辑体验打磨成本高 | **推荐（MVP）** |
| 第三方 Compose 富文本 / Markdown 编辑器库 | 富文本 | 起步快 | 维护状态、许可证、与块模型契合度需逐一评估 | Phase 0 评估 |
| WebView + 同一套 JS 编辑器 | 源码 + 预览 | 两端行为一致 | 在 Android 上引入 WebView 与 JS 桥 | 备选 |

### 4.3 两端一致性原则

> 允许两端**外观**不同，不允许**语义**不同。语义（解析、规范化、渲染数据）全部在核心，壳只决定样式。若某一端使用第三方库，必须用它**仅做展示**，或用它输出的 Markdown 回传给核心——不允许它成为格式的权威。

## 5. 不支持的语法与降级策略

| 输入 | 处理 |
| --- | --- |
| 内联 HTML | 保留原文（作为纯文本），渲染时显示为文本，不执行 |
| 脚注 / 数学 / 自定义容器 | 以"未知块"保留原文与位置，渲染为代码块样式，不丢内容 |
| 超长单行（> 64 KiB） | 接受但提示性能风险 |
| 二进制/图片以外附件 | 转化为附件引用（``blob:<sha256>` 链接`），附件按需拉取 |
| 从其它编辑器粘贴的 HTML | 壳先经"HTML → Markdown 转换"（壳层或核心的宽松降级器），无法转换的删减并**提示用户**，不静默 |

## 6. 渲染与预览

- `notes.render` 返回块列表；壳负责样式（字体、间距、代码块主题、暗色模式）。
- 代码块高亮：由壳的语法高亮组件完成（两端库不同），核心只给语言标注。
- 表格在窄屏（Android）的实现：横向滚动或堆叠显示，属于壳的样式决策。

## 7. 待验证

1. 块 id 在"编辑中间块"时是否稳定（删除/插入是否导致整段重排）。
2. 表格、嵌套列表、任务列表的规范化在两个方向（源码 ↔ 块模型）是否完全可逆（Phase 0 往返测试：`parse → render → serialize` 必须等于 `body_norm`）。
3. 富文本控件的输入法（IME）在 Android 上与 Compose 的兼容性（组合输入期间 `rev_id` 频繁变化会制造大量修订，需要合并提交策略——草案：静默 500 ms 后提交一个修订）。
