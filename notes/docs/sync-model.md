# 同步模型：night-clip-notes

> 决策记录：[ADR-001](adr/001-notes-sync-and-storage.md)。传输层位置见 [architecture.md](architecture.md) §4。
> 本文定义"两台设备各编辑一篇笔记后，最后都收敛到同一内容"的规则与可测试保证。**本文描述的是已实现的行为**（`core/notes/`）；与最初草案不同之处集中记在 §9。

## 1. 目标与不变量

1. **离线优先**：设备可以长时间离线编辑，重连后补发；不阻塞编辑。
2. **最终一致**：所有可达设备最终持有相同的笔记集合与相同的每篇笔记内容。
3. **交换律**：同步顺序不影响最终结果（属性测试验收）。
4. **幂等**：同一修订重复推送、重复确认都是 no-op。
5. **不丢用户输入**：无法自动合并的冲突保留为**冲突副本**，绝不静默丢弃。
6. **删除可传播**：删除产生墓碑，不会被旧设备"复活"。

## 2. 数据与版本

两台设备之间**只交换修订**。修订不可变、由内容寻址，所以一台设备持有的修订集合只会增长（grow-only set）：这是"交换律 / 幂等 / 收敛"的根基。

每篇笔记的修订构成一张有向无环图（DAG）：

```text
note(note_id)
  rev_1 ← rev_2 ← rev_3          （普通编辑：一个父修订）
              ↖        ↘
                 rev_4' ← merge  （合并修订：多个父修订）
```

| 字段 | 作用 |
| --- | --- |
| `rev_id` | `"r_" + hex(sha256("clipbridge.notes.rev.v1\0" + 规范 JSON{note_id, parents, title, body, format_version, origin_device, created_at, deleted, conflict_of}))[:32]`。两端对同一修订算出同一个 id |
| `parents` | 父修订 id（已排序）。**数组**而不是草案里的单个 `parent_rev`：合并修订有多个父 |
| `title` / `body` | 标题（单行、无控制字符）与规范化 Markdown 正文（[editor-and-markdown.md](editor-and-markdown.md) §2）。哈希的是规范化后的字节 |
| `origin_device` / `created_at` | 设备 id（合并修订为常量 `"merge"`）与毫秒时间，用于打破平局与展示"谁改的" |
| `deleted` | 墓碑标记。删除 = 追加一个 `deleted:true` 的修订，恢复 = 再追加一个 `deleted:false` 的修订 |
| `conflict_of` | 该笔记是哪篇笔记的冲突副本；空表示普通笔记。随修订链向后继承，直到用户裁决 |

> 用"修订图 + 内容哈希"而不是"整篇版本号 + 最后写入胜出（LWW）"的唯一原因：LWW 在两端各改一段时必然丢一端的内容。修订图让核心能判断"是否分叉"。

**不变量**：一个修订只有在它的**全部父修订**都已入库之后才会入库（`store.ErrMissingParent`）。因此本地持有的图总是祖先闭包完整的，两端 head 相同 ⇔ 修订集合相同。

**接收时的校验**（`validateWire`，对端不被信任）：id 必须等于内容哈希；标题/正文必须已是规范形式（否则同一文本在不同设备上会规范化出不同的 id）；大小不超限（正文 1 MiB、标题 1 KiB）；`format_version` 高于本端支持时单独报 `UNSUPPORTED_FORMAT`（同步状态显示"请升级"），而不是当作垃圾数据。

## 3. 同步流程

传输是已认证连接上的 HTTP 路由，不占用 WebSocket 事件通道（决策见 [architecture.md](architecture.md) §4）。与密码库同步一致：**拨号一侧发起，监听一侧只应答**；拨号侧每轮把两个方向都做完。

1. **探测**：`GET /v1/notes/head` 返回对端的计数器 `seq`（每存入一个修订加一，仅在该设备内有意义）。拨号侧记着上一轮完整结束时两端的计数器；两者都没变就什么都不做。
2. **摘要**：`GET /v1/notes/digest?after=<note_id>` 分页返回 `note_id → head 修订列表`（不含正文）。
3. **拉取**：对端 head 里有本端没有的修订的笔记，`POST /v1/notes/pull`，带上本端 head 及其最近 64 个祖先作为 `have`；对端返回"它有而 `have` 的祖先闭包里没有"的全部修订，父在前。一次答不完（400 个修订 / 约 6 MiB）则 `more` 指明哪些笔记要续拉。
4. **应用并合并**：收到的修订在**一个事务**里校验入库，然后对涉及的笔记执行 §4 的 head 解析。
5. **推送**：本端 head 与对端不同的笔记，`POST /v1/notes/push` 发送"对端 head 祖先闭包之外"的全部修订（包含第 4 步产生的合并修订）。
6. **记账**：成功后记录两端计数器、时间，状态回到 `idle`；对端的修订被拒绝（校验失败）则状态为 `error` 并带说明。

对端收到推送后同样执行第 4 步。两端拥有相同的修订集合后，head 解析是该集合的纯函数，所以两端各自算出的合并修订**逐字节相同**，一轮之后就收敛。

**本机编辑立即触发一轮**（`Kick`），拨号侧还每 10 秒轮询一次。监听侧（通常是 Windows）的本机编辑要等拨号侧下一次轮询才会到达（最长约 10 秒）；没有沿用剪贴板的 control 帧去"敲门"，因为那会进入持久化发件箱并占用序号，影响现有链路语义。

7. **附件**（见 §10）：修订交换完成后，拨号侧再交换"某篇笔记当前文本引用着"的附件。

**尚未实现**：修订链压缩与淘汰、回收站 30 天后的物理清理（见 §8）。当前所有修订都保留。

## 4. Head 解析与合并

一篇笔记的 head 是"没有后继的修订"。多于一个 head 就是分叉。`reconcile` 的规则：

| 情况 | 处理 |
| --- | --- |
| 恰有一个 head | 就是当前版本，更新列表行（标题、预览、时间、墓碑、`conflict_of`） |
| 多个 head | 把它们按 id 排序后依次两两合并，**生成一个新的合并修订**：父 = 全部 head，`origin_device = "merge"`，`created_at` = 各 head 的最大值，内容是合并结果。该修订的 id 只取决于 head 与它们的祖先，所以每台设备算出同一个 |
| 共同祖先 | 两个 head 的祖先闭包的交集里取"没有子孙也在交集里"的修订；多个时取 `(created_at, origin, rev_id)` 最大者。没有共同祖先时，以空内容为基 |

合并两个 head（`base` 为共同祖先）：

| 两个 head | 结果 |
| --- | --- |
| 都已删除 | 删除，内容取较新的一个 |
| 一个删除、一个没删 | 没删的那个相对 `base` **没有改动** → 删除成立；有改动 → 编辑保留（笔记不被删），并发出 `deleted_elsewhere` 通知。"删除只胜过没人动过的对象" |
| 都没删 | 标题与正文**分别**做三路合并，两者都成功才算合并成功 |

- **正文三路合并**：按 Markdown 块（[editor-and-markdown.md](editor-and-markdown.md) §3）。对 `base→左` 与 `base→右` 分别做块序列的最长公共子序列比对，得到互不重叠的改动段；两边改动的块范围**不重叠**（相邻不算重叠）就按基准位置顺序拼接，两边做了完全相同的改动只算一次；同一位置两处不同的插入视为冲突。合并是**对左右对称**的纯函数（`merge3(b,l,r) = merge3(b,r,l)`，有属性测试）。比对格子数超过预算（400 万）时退化为"一整段改动"，此时只要两边都改了就是冲突。
- **块内按行合并**：两边改了**同一个块**（且各自仍是一个块）时，再把这个块按行做一次同样的三路合并——清单里两人各改一项、同一段落改不同的行、各自往列表末尾加一项，都不再产生副本。合并结果再过一遍规范化（两处各自合法的列表编辑合在一起可能不是规范形式）。同一行被两边改成不同内容仍然是冲突。是否要进一步做词级合并见 [crdt-evaluation.md](crdt-evaluation.md)。
- **标题三路合并**：只有一边改了就取改的一边；两边改成不同的值是冲突。

### 4.1 冲突副本

块级合并失败（两边改了同一块，或同时改了不同的标题）时：

1. `(created_at, origin_device, rev_id)` 更大的一边作为笔记正文（合并修订的内容）。
2. 较旧的一边成为**冲突副本**：一篇新笔记，标题 = 原标题 + `（冲突 来自 <设备id前缀> <UTC 时间>）`，正文顶部插入一个以"冲突副本："开头的引用块说明来源，下面是被放在一边的完整正文。
3. 副本的 **`note_id` 是被放在一边的内容的函数**（`sha256(原 note_id, 标题, 正文)`），首个修订的时间、作者取自被放在一边的修订。因此每台设备独立得到**同一篇**副本、同一个 rev_id，不会各生成一份（对应草案里的"副本内容相同只保留一份"）。
4. 通知：`notes.sync.conflict`（`reason: "diverged"`）。副本本身是普通笔记，照常同步。
5. 用户裁决（`notes.sync_resolve`）：`keep_main`（丢弃副本）、`keep_conflict`（副本内容放回原笔记）、`merge`（副本正文接在原笔记后）；之后副本被移入回收站。裁决是普通的编辑/删除修订，会同步到其它设备。已被裁决的副本不会"复活"：重新计算出的副本首修订与已有的相同，是 no-op。

> 为什么 MVP 不做字符级 CRDT：需要为富文本引入 CRDT 的数据模型与持久化格式，且与"Markdown 为权威存储"（ADR-002）叠加后，编辑器必须能读写 CRDT 状态；复杂度和调试成本远高于块级合并 + 冲突副本，而后者已经满足"不丢内容"的底线。字符级协作列为 Phase 2 候选，见 [ADR-001](adr/001-notes-sync-and-storage.md) 替代方案。

### 4.2 本机编辑也走同一条路

`notes.update` 带 `base_rev_id`：编辑是 `base_rev_id` 的子修订。`base_rev_id` 不是最新修订时，这个子修订与最新修订就是两个 head，由同一个 `reconcile` 合并。所以"本机在旧版本上编辑"与"另一台设备并发编辑"是同一种情形，没有第二套规则。

## 5. 删除与恢复

- 删除 = 追加墓碑修订；恢复 = 在墓碑后再追加 `deleted:false` 的修订。回收站里的笔记不能编辑（`CONFLICT`）。
- 一台设备收到墓碑，而它本机的某个 head 是墓碑的祖先 → 直接快进到墓碑（不是分叉）。
- 旧设备之后再推送旧修订：它们是墓碑的祖先，不影响 head，**不会复活**。
- 删除与并发编辑的取舍见 §4 表格。
- 回收站"30 天后物理清理"**尚未实现**：当前墓碑与回收站内容永久保留。物理清理需要"所有已配对设备都已收到这个墓碑"的前提（否则离线设备会让笔记复活），见 §8 的设计结论。

## 6. 离线、重试与 TTL

- 现有剪贴板事件的**发件箱 + TTL** 语义**不套用**：笔记修订不过期，对端上线后由拨号侧补齐。
- 同步可中断、可续传：摘要分页、按笔记拉取、一轮失败则下一轮从头再来（已入库的修订是幂等的）。
- 不设"超过 N 天就丢弃"。

## 8. 已知代价与未实现

- 修订图会增长（每次自动保存是一个修订，两端都用"停顿 500 ms 后保存"，一次长时间的输入会产生很多修订）；压缩与淘汰（草案里"保留最近 50 个 + 对端低水位"）**未实现**。
- 回收站物理清理未实现（§5）。
- **压缩与清理的设计结论**（尚未动手，原因是风险高于收益）：二者都需要"对端已经收到了什么"的水位。拨号侧已经记录 `our_seq`（推送过的范围），监听侧却不知道拨号侧收到了什么，所以需要拨号侧在探测请求里带上它已完整处理的对端 `seq`，监听侧据此为每个对端记一个确认水位。有了双向水位之后，才能安全地：删除"所有对端都已确认收到墓碑、且超过 30 天"的整篇笔记；把"所有对端都已确认的祖先"折叠成快照。还要处理两个边界：撤销配对后又重新配对的设备带着旧数据回来（会让已清理的笔记复活，只能提示）、清理与拉取的竞争（一端已清理、另一端还没清理时，拉取会把整篇笔记再拉回来，需要让清理只在拨号侧发起并由监听侧同轮确认）。把"本机连续自动保存"合并成一个修订（squash）也不能做：对端可能已经拉走了其中一个修订，之后会被当成分叉并产生冲突副本。
- 冲突副本对用户是额外心智负担；块级合并的覆盖率决定了副本出现频率，同一块内两处编辑一定产生副本，需要真实使用数据。
- 修订的作者没有签名，信任来自配对时固定的证书（与主仓库一致）；已配对的设备可以写出任意内容、任意时间的修订，最坏情况是它的编辑总是"较新"，但不会让任何内容丢失（旧内容在历史里，冲突内容在副本里）。
- 搜索索引只在内存里（见 §11）。
- **规范化形式是线路协议的一部分**：接收时要求正文已经是本端规范化器的输出（否则同一文本在不同设备上会得到不同的 `rev_id`）。因此两台设备上的规范化器必须一致——同一个 Go 版本构建、同一个 `markdown.FormatVersion`。改变规范化输出的修改需要升级 `FormatVersion`，并让新版本能按旧规则校验旧修订（目前只实现了当前版本）；在此之前，`core/notes/markdown` 的 golden 测试就是规范形式的"钉子"。两端 App 不同步升级、规范化行为不同时，同步状态会显示错误并说明有多少修订被拒绝。

## 9. 与最初草案的差异

| 草案 | 实现 | 原因 |
| --- | --- | --- |
| `parent_rev`（单个） | `parents`（数组） | 合并修订有多个父修订；让合并成为"每台设备算出同一个修订"，而不是互相交换合并结果 |
| 笔记帧在 WebSocket 上分流（`notes.hello` 等） | `/v1/notes/*` HTTP 路由，同一 mTLS 端口 | P0-3：避免与剪贴板/文件共用通道、不碰事件序号语义；复用密码库同步已有的做法 |
| 握手交换 challenge 防止"同库误配对" | 无 | 笔记没有"同一个库"概念：任何已配对设备的笔记都合并进来 |
| 冲突副本"新建一篇笔记" | `note_id` 由被放在一边的内容决定 | 各设备独立生成时必须得到同一篇 |
| 标题后缀含设备名 | 含设备 id 前缀 | 设备名只在本机已知，不同设备会生成不同标题，破坏一致 |
| 时间单位 | 毫秒 | 同一秒内多次编辑也要有确定顺序 |
| 全文搜索用 SQLite FTS5 | 内存索引 | FTS5 会把明文倒排索引写到磁盘，笔记在库里是加密的（§11） |
| 附件"只在对端请求时传输" | 拨号侧双向搬运"被引用的附件" | 监听侧不能向拨号侧发请求（§10） |

## 10. 附件

- 附件是按内容哈希（SHA-256）命名的文件，存在 `note_blobs`（数据与文件名都用数据库密钥加密）；笔记里用 `blob:<sha256>` 链接引用（[api-spec.md](../api-spec.md) §2.2）。相同内容只存一份，单个上限 32 MiB。
- `note_blob_refs` 记录每篇笔记**当前文本**引用了哪些附件（每次 `reconcile` 更新；回收站里的笔记也算，这样在别处恢复它时图片不会缺失）。
- 同步的是被引用的附件，不是全部：拨号侧每轮在修订交换之后，用 `POST /v1/notes/blob_have` 问对端有哪些，缺的用 `GET /v1/notes/blob/<id>` 取，对端缺的用 `PUT /v1/notes/blob/<id>` 送过去。和修订不同，这是**积极同步**而不是"对端请求才传"：监听侧不能主动向拨号侧请求，所以由拨号侧负责双向搬运；代价是一篇带大图的笔记会在同步时把图传到另一台设备。
- 接收方**不信任**对端：字节的 SHA-256 必须等于 id；大小不超限；而且必须有某篇笔记当前引用它，否则拒收（已配对的设备不能往你的库里随便塞文件）；文件名与类型被清理（控制字符、非法类型 → `application/octet-stream`）；同一时刻只读一个上传。
- 清理：`notes.attachment_cleanup` 只删除"任何修订（含历史）都不再引用且超过 7 天"的附件，由用户手动触发。
- 图片只按 PNG / JPEG / GIF / WebP / BMP 内联显示；SVG 当作普通文件链接（它可以带脚本）。壳绝不把 `blob:` 当网址打开，也不自动运行下载的文件。
- 不在导出里：ZIP 导出只有 Markdown，`blob:` 链接保留在文本中。

## 11. 搜索

- 全文搜索用**内存索引**，没有用计划里写的 SQLite FTS5：笔记在库里是加密存储的，FTS5 会把明文的倒排索引写到磁盘上，破坏这个保证。内存索引在第一次搜索时由各篇笔记的当前文本建立，之后每次搜索只重读"当前修订变了"的笔记（对比 `head_rev`），所以新到达的同步内容、编辑、删除、恢复都自然反映在结果里。
- 匹配是不区分大小写的子串，所有词都要出现，所以中日韩文本不需要分词；标题命中优先，其次出现次数、再其次较新。每篇笔记最多索引前 512 KiB 的文本。进程重启后索引重建（几千篇笔记是毫秒级到百毫秒级）。
