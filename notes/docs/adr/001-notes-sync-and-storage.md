# notes ADR-001：笔记同步与存储模型（修订链 + 块级合并 + 冲突副本）

- 日期：2026-10-27
- 决策者：待定（项目组）
- 相关文档：[architecture.md](../architecture.md)、[sync-model.md](../sync-model.md)、[../api-spec.md](../../api-spec.md)、[ADR-002](002-rich-text-and-markdown.md)、主仓库 `docs/adr/005-go-core-and-tailnet-p2p.md`

## 背景

笔记是用户长期积累的私有数据，需要 Windows 与 Android 两端：

1. 离线可编辑，重连后同步；
2. 多端编辑后最终一致，且**不能丢用户内容**；
3. 无服务端，只在已配对设备间经 tailnet 直连传输；
4. 复用 night-clip 现有身份、配对、链路与存储，不复制协议。

现有可参考的两种现成做法都不完全适用：

- **剪贴板事件**：发件箱 + 序号 + TTL 过期丢弃。笔记不能过期丢弃，且需要"双向补齐"而不是"广播最新值"。
- **密码库同步**：整库文件传输 + 解锁后按 KeePass 规则合并。笔记是逐条细粒度编辑，整库合并的粒度和成本都不合适。

## 决策

1. **同步粒度是笔记条目（note）与它的不可变修订（rev）**，不是整库、不是文件。
2. **修订链模型**：每篇笔记有修订链 `rev_1 ← rev_2 ← …`，`rev_id` 由规范化正文与元数据的内容哈希确定（跨端可复现）。`parents`（数组）指向父修订；合并产生的修订有多个父。
3. **合并是纯函数**：修订集合只增不减；多个 head 的合并结果只取决于这些 head 及其祖先，每台设备算出**同一个合并修订**（同一个 `rev_id`），所以满足交换律与幂等，同步顺序不影响最终结果。
4. **分叉处理 = 块级自动合并，不能合并则确定性胜出 + 冲突副本**：基于两端的共同祖先，若改动落在不同 Markdown 块则合并；否则按 `(created_at, origin_device, rev_id)` 确定性选出主线，落后版本保留为独立笔记（其 `note_id` 由被放在一边的内容决定，各设备得到同一篇）并在 UI 提示。**永不静默丢弃用户输入。**
5. **删除是墓碑修订**，按"删除只胜过没动过的对象"传播；回收站 30 天后物理清理。
6. **同步传输是同一 mTLS 服务器上的 HTTP 路由**（`/v1/notes/head|digest|pull|push`），按修订搬运，拨号方发起、监听方应答；不占用剪贴板/文件的 WebSocket 通道（做法同密码库同步）。
7. **存储**：同一个 SQLite 库，新增 `notes`、`note_revs` 等表；正文 = 规范化 Markdown；全文索引**只放在内存里**（不是最初写的 FTS5：笔记在库里是加密的，FTS5 会把明文倒排索引写到磁盘）。
8. **MVP 不做字符级 CRDT**（见替代方案）。

## 替代方案

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 整篇 LWW（最后写入胜出） | 不采用 | 实现最简单，但两端各改一段时必丢一端内容，违背硬要求 |
| 整库文件同步（沿用密码库模式） | 不采用 | 编辑一次要传输全部笔记；无法逐条合并与补发 |
| 字符级 CRDT（如 Yjs/Automerge 类方案） | Phase 2 候选 | 需要为富文本定义 CRDT 数据模型并持久化其状态，与"Markdown 为权威存储"叠加后编辑器必须读写 CRDT；复杂度高。块级合并 + 冲突副本已满足"不丢内容" |
| 自定义三路合并（diff3） | 不采用（作为块合并的补充可考虑） | 富工具栏结构下纯文本三路合并会产出损坏的 Markdown |
| 每次同步全量摘要 | 采用为协议简化形式 | 摘要只含 `note_id → 最新 rev_id`，体积可控；不做增量索引的优化 |

## 结果

### 正面

- 不丢内容；删除、离线、并发编辑都有明确规则。
- 合并是纯函数 → 可以用属性测试证明交换律/幂等/收敛（做法与密码库同步一致）。
- 传输粒度小，断网后补发成本低；无服务端，无配额。

### 负面

- 冲突副本会带来用户心智负担，出现频率取决于块级合并覆盖率（Phase 0 需实测）。
- 修订链需要淘汰与压缩，压缩窗口与慢设备离线时长耦合。
- 墓碑清理后，长期离线设备可能"复活"已删笔记（已定义缓解措施，但不能完全避免）。
- "内容哈希作为 rev_id"要求两端规范化实现**完全一致**；规范化有任何漂移都会导致重复修订与误判分叉（Phase 0 往返测试必须锁死）。
